# שלב 11ב — Workflow לאישור תוכן

## 1. מטרה

בארגון שמפעיל את האפשרות, שינוי של עורך שמשפיע על המסכים לא עולה לאוויר עד שמנהל מאשר אותו. כך מורה מעדכנת הודעה, והמנהלת מאשרת לפני שזה מוצג בכל בית הספר.

## 2. User Stories

1. **מנהל:** מפעיל "אישור תוכן" בהגדרות הארגון.
2. **עורכת:** שומרת שינוי ברשימת השמעה. השינוי נבדק מיד, ושגיאות מוצגות כרגיל. אם הוא תקין, היא רואה "השינוי נשלח לאישור", והמסכים עדיין מציגים את הגרסה הקודמת.
3. **מנהל:** מקבל אימייל, ורואה בדף "ממתין לאישור" מי ביקש, מה וממתי. הוא מאשר (השינוי עולה למסכים מיד) או דוחה עם הערה.
4. **עורכת:** רואה בדף את מצב הבקשות שלה: ממתינה, אושרה או נדחתה, כולל ההערה.
5. **כולם:** התראות חירום **אף פעם** לא ממתינות לאישור.

## 3. מה דורש אישור

כשהאפשרות פעילה, ותפקיד המבקש הוא `EDITOR`:

| ישות         | פעולות שממתינות לאישור       |
| ------------ | ---------------------------- |
| רשימות השמעה | עריכה, תוכן, מחיקה           |
| Widgets      | עריכה, מחיקה                 |
| תבניות       | עריכה, מחיקה                 |
| לוחות זמנים  | עריכה, מחיקה                 |
| מסכים        | עריכה (שיוך תוכן, שם, כיוון) |
| מדיה         | מחיקה                        |

**מה לא דורש אישור:**

- **יצירה ושכפול:** תוכן חדש לא מוצג באף מסך עד שמשייכים אותו, והשיוך עצמו דורש אישור.
- **העלאת מדיה:** אותה סיבה.
- **התראות חירום.**
- **פעולות של `ADMIN` ו-`OWNER`.**

## 4. איך זה עובד (בלי לשכתב את המודולים)

**הבקשה של העורך:**

1. הבקשה רצה **במלואה** בתוך טרנזקציית הבקשה (זו שקיימת כבר בשביל RLS), כולל כל הבדיקות ואילוצי המסד.
2. אם היא הצליחה, הטרנזקציה **מתבטלת** (rollback). גם הודעות למסכים מתבטלות, כי הן ממילא נשלחות רק אחרי commit.
3. נשמרת בקשה ממתינה: השיטה, הנתיב, גוף הבקשה ותקציר (סוג ושם).
4. התשובה לעורך: `202 { approval }`.

**האישור:** הבקשה המקורית רצה שוב, **בשם המנהל המאשר** (בקשה פנימית עם ה-session שלו). התוכן נבדק מחדש מול המצב הנוכחי.

- **אם היא נכשלת עכשיו** (למשל, הפריט נמחק בינתיים), הבקשה נשארת ממתינה, והמנהל רואה את השגיאה.
- **שני מנהלים שמאשרים בו זמנית:** השורה ננעלת, והבקשה מיושמת פעם אחת בלבד.

**בלי RLS:** כשה-RLS כבוי, נפתחת טרנזקציה רגילה רק לבקשות שממתינות לאישור.

## 5. מודל נתונים (מיגרציה `0013_approvals`)

```
organizations.require_approval boolean DEFAULT false

approval_requests
  id, org_id (RLS), method, path, body jsonb (≤ 1MB), summary jsonb {kind, name, action}
  status 'pending' | 'approved' | 'rejected' | 'withdrawn'
  requested_by, requested_at, decided_by, decided_at, note (≤ 500)
```

**תקרה:** 100 בקשות ממתינות לארגון.

## 6. ‏API

| Method | Path                                         | הרשאה  | תיאור                                                      |
| ------ | -------------------------------------------- | ------ | ---------------------------------------------------------- |
| GET    | `/api/v1/orgs/:orgId/approvals?status=`      | VIEWER | ‏EDITOR ו-VIEWER רואים רק את הבקשות שלהם, ‏ADMIN רואה הכול |
| POST   | `/api/v1/orgs/:orgId/approvals/:id/approve`  | ADMIN  | מיישם את הבקשה                                             |
| POST   | `/api/v1/orgs/:orgId/approvals/:id/reject`   | ADMIN  | דחייה. גוף הבקשה: `{ note? }`                              |
| POST   | `/api/v1/orgs/:orgId/approvals/:id/withdraw` | המבקש  | ביטול של בקשה ממתינה                                       |

**שינוי בהגדרות:** ‏`PATCH /api/v1/orgs/:orgId` מקבל עכשיו גם `requireApproval`.

## 7. Threat Model קצר

| איום                 | בקרה                                                                                    |
| -------------------- | --------------------------------------------------------------------------------------- |
| עורך שעוקף את האישור | השער נמצא בשרת, לפי התפקיד מהמסד. כותרות HTTP לא משפיעות עליו. האישור רץ כבקשה של המנהל |
| בקשה שאושרה פעמיים   | נעילת שורה, ומעבר מ-`pending` ל-`approved` רק פעם אחת                                   |
| ‏IDOR                | ‏`orgGuard` ו-RLS. הנתיב השמור חייב להתחיל ב-`/api/v1/orgs/<אותו ארגון>/`               |
| הצפת בקשות           | תקרה של 100 בקשות ממתינות, ומגבלת הגודל הקיימת על גוף הבקשה                             |
| מידע אישי            | גוף הבקשה הוא תוכן (טקסטים ושיוכים), כמו התוכן עצמו. נשמר עד החלטה ועוד 90 יום          |

## 8. נגישות

- **דף "ממתין לאישור":** טבלה נגישה, כפתורים עם שמות מלאים, ואישור לפני דחייה.
- **הודעת "נשלח לאישור":** מוצגת כמידע, לא כשגיאה, ומוכרזת (`role="status"`).

## 9. בדיקות

- **‏API:**
  - שער לעורך בלבד, ולא למנהל.
  - בקשה לא תקינה נדחית מיד, ולא נשמרת.
  - הרצה לניסיון שלא משנה כלום ולא שולחת הודעה למסכים.
  - אישור שמיישם ושולח הודעה למסכים.
  - דחייה וביטול.
  - אישור כפול.
  - בקשה שכבר לא תקפה.
  - בידוד בין ארגונים.
  - התראות חירום לא נחסמות.
- **מסך הניהול:** הודעת "נשלח לאישור" ודף האישורים.
- **‏E2E:** עורכת שומרת, המסך לא משתנה, מנהל מאשר, והמסך משתנה.

## 10. תוצאות

**שרת:**

- מיגרציה `0013` (עם RLS).
- ‏`modules/approvals`: שער (`approvalGate`) ונתיבים.
- ‏`lib/tenant.ts` קיבל מצב "הרצה לניסיון": הבקשה רצה במלואה, מתבטלת (rollback), והתשובה מוחלפת ב-`202` לפני השליחה.
- השער נוסף ל-11 נתיבים ב-6 מודולים, בלי לשנות את ה-handlers.
- מנהלים מקבלים אימייל.
- בקשות שהוכרעו נמחקות אחרי 90 יום.

**מסך הניהול:**

- דף "אישורים" (בתפריט רק כשהאפשרות פעילה): אישור, דחייה עם הערה, ביטול בקשה, והיסטוריה.
- ‏`ApprovalPendingError` מוצג כמידע (`role="status"`) ולא כשגיאה, בכל טופס ועורך. הטופס שומר את מצבו.
- תיבת סימון בהגדרות הארגון.

**בדיקות:**

- 6 בדיקות API:
  - בלי האפשרות, השינוי עולה ישר. רק מנהל מפעיל אותה.
  - הרצה לניסיון: בקשה לא תקינה נדחית מיד, הנתונים לא משתנים ולא נשלחת הודעה למסכים. אחרי אישור יש שינוי והודעה, ואישור כפול נדחה.
  - מחיקה ותוכן של רשימת השמעה ממתינים לאישור. יצירה, פעולות מנהל והתראות חירום לא.
  - דחייה עם הערה. רק המבקש יכול לבטל, ועורך לא יכול להחליט. בקשה שכבר לא תקפה נשארת ממתינה ומוסברת.
  - גם בלי RLS.
  - בידוד בין ארגונים, כולל בדיקת ה-IDOR הכללית.
- 3 בדיקות במסך הניהול, כולל ההודעה כמידע ולא כשגיאה.
- ‏E2E: מורה שומרת, השינוי לא חל, היא רואה את הבקשה, מנהל מאשר (כולל axe), והשינוי חל.
- בדיקת הגיבוי מוודאת עכשיו 18 מדיניות.
