# שלב 11א — התחברות דרך הארגון (SSO, ‏OpenID Connect)

## 1. מטרה

מורים ועובדים מתחברים עם החשבון הארגוני שלהם (Google Workspace, ‏Microsoft Entra ID, ‏Keycloak וכל ספק OIDC אחר), בלי סיסמה נוספת לנהל. הגדרה אחת של המפעיל משרתת את כל השרת.

## 2. User Stories

1. **מפעיל:** מגדיר ב-`.env` כתובת ספק, ‏Client ID ו-Client Secret, וכפתור "התחברות עם …" מופיע במסך הכניסה.
2. **משתמש קיים:** מתחבר דרך הספק, ומזוהה לפי אימייל מאומת. מההתחברות הבאה הוא מזוהה לפי המזהה הקבוע שהספק נותן (`sub`).
3. **מורה שהוזמנה (מצב הזמנות):** לוחצת על כפתור ה-SSO. החשבון נוצר רק אם יש הזמנה פתוחה לאימייל שלה, והיא מצטרפת לארגון.
4. **מנהל:** רואה ביומן הביקורת שההתחברות הייתה דרך SSO.
5. **משתמש עם MFA מקומי:** מתבקש גם את הקוד, כמו בהתחברות רגילה.

## 3. החלטות

**ספק אחד לשרת, מוגדר במשתני סביבה:**

| משתנה                  | תפקיד                                     |
| ---------------------- | ----------------------------------------- |
| `OIDC_ISSUER`          | כתובת הספק                                |
| `OIDC_CLIENT_ID`       | מזהה האפליקציה אצל הספק                   |
| `OIDC_CLIENT_SECRET`   | הסוד של האפליקציה                         |
| `OIDC_NAME`            | הטקסט על כפתור ההתחברות                   |
| `OIDC_ALLOWED_DOMAINS` | רשות: רק אימיילים מהדומיינים האלה מתקבלים |

- **ספק לכל ארגון:** נדחה לגרסה מאוחרת יותר.
- **כתובת החזרה (redirect URI) קבועה:** `${PUBLIC_URL}/api/v1/auth/oidc/callback`. המפעיל רושם אותה אצל הספק.

**הזרימה (Authorization Code עם PKCE):**

1. `GET /api/v1/auth/oidc/start` יוצר `state`, ‏`nonce` ו-PKCE verifier, שומר אותם ב-Valkey ל-10 דקות לפי `state`, ומפנה לספק.
2. `GET /api/v1/auth/oidc/callback` בודק את ה-`state` (חד-פעמי), מחליף את הקוד בטוקן (`openid-client` בודק את חתימת ה-ID Token, ‏`iss`, ‏`aud`, ‏`exp` ו-`nonce`), ומקבל את `sub`, ‏`email` ו-`email_verified`.

**התאמת משתמש:**

1. קודם לפי `(issuer, sub)` בטבלה החדשה `user_identities`.
2. אחר כך לפי אימייל, **רק אם `email_verified` הוא true**. אז הזהות מקושרת אוטומטית.
3. משתמש חדש נוצר לפי `REGISTRATION_MODE`:
   - `open`: נוצר.
   - `invite`: רק עם הזמנה פתוחה. ההזמנה מתקבלת אוטומטית.
   - `closed`: לא נוצר.
4. משתמש שנוצר דרך SSO מקבל סיסמה אקראית שאינה ניתנת לשימוש. אם ירצה בעתיד סיסמה, ישתמש ב"שכחתי סיסמה".

**אחרי ההתאמה:**

- **‏MFA:** אם למשתמש יש MFA מקומי, הוא מקבל את אותו אתגר כמו בהתחברות רגילה.
- **חזרה לאתר:** חזרה רק לנתיב יחסי פנימי (`returnTo` שמתחיל ב-`/` ולא ב-`//`), כדי למנוע Open Redirect.

## 4. מודל נתונים (מיגרציה `0012_user_identities`)

```
user_identities
  user_id uuid FK → users (cascade)
  issuer text, subject text   UNIQUE (issuer, subject)
  email text                  -- the email at the time of linking, for display only
  created_at, last_used_at timestamptz
```

**נגישות לפי RLS:** הטבלה לא נגישה לתפקיד `rubinny_tenant`. ההתחברות היא נתיב מערכת.

## 5. ‏API

| Method | Path                                | הרשאה                | תיאור                                                        |
| ------ | ----------------------------------- | -------------------- | ------------------------------------------------------------ |
| GET    | `/api/v1/auth/providers`            | ציבורי               | `{ oidc: { name } \| null }`                                 |
| GET    | `/api/v1/auth/oidc/start?returnTo=` | ציבורי, עם מגבלת קצב | הפניה (302) לספק                                             |
| GET    | `/api/v1/auth/oidc/callback`        | ציבורי, עם מגבלת קצב | יוצר session, או מבקש MFA, ומפנה חזרה                        |
| GET    | `/api/v1/me/identities`             | משתמש מחובר          | הזהויות המקושרות                                             |
| DELETE | `/api/v1/me/identities/:id`         | משתמש מחובר          | ניתוק זהות. מותר רק אם יש סיסמה מקומית בשימוש, או זהות נוספת |

**שגיאות:** מופיעות כהפניה ל-`/login?sso=<code>`, למשל `not_invited`, ‏`unverified_email`, ‏`domain`, ‏`expired` או `failed`, עם הודעה נגישה בעברית ובאנגלית. **בלי פרטים טכניים.**

## 6. Threat Model קצר

| איום                                 | בקרה                                                                                                                    |
| ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------- |
| ‏CSRF בהתחברות, או שימוש חוזר בקוד   | `state` חד-פעמי ב-Valkey, ‏PKCE (S256), ו-`nonce` ב-ID Token                                                            |
| השתלטות על חשבון דרך אימייל שלא אומת | קישור לפי אימייל רק כש-`email_verified` הוא true. אחרי הקישור הזיהוי לפי `sub` בלבד                                     |
| מישהו נרשם מראש עם האימייל של אחר    | אם החשבון הקיים לא אומת אף פעם, הקישור מאפס אותו: הסיסמה, ‏MFA, קודי השחזור, הקישורים וה-sessions הקודמים מפסיקים לעבוד |
| אימייל מדומיין זר                    | `OIDC_ALLOWED_DOMAINS`                                                                                                  |
| ‏Open Redirect                       | `returnTo` יחסי בלבד, ונבדק בשרת                                                                                        |
| ‏ID Token מזויף                      | `openid-client` בודק חתימה מול ה-JWKS של הספק, ואת `iss`, ‏`aud`, ‏`exp` ו-`nonce`                                      |
| דליפת סוד                            | ‏`OIDC_CLIENT_SECRET` נמצא רק במשתנה סביבה, ומצונזר בלוגים                                                              |
| ‏SSRF                                | ה-`issuer` נקבע על ידי המפעיל בלבד, ולא על ידי משתמשים                                                                  |
| עקיפת MFA                            | ‏MFA מקומי נדרש גם אחרי SSO                                                                                             |

## 7. פרטיות

**מה נשמר:** ‏`issuer`, ‏`sub` והאימייל בזמן הקישור. זה מינימום הנתונים, וזה נכלל בייצוא ובמחיקה של החשבון.

**ספק הזהות:** צד שלישי שהמפעיל בוחר. הספק יודע מתי המשתמש התחבר ל-Rubinny. יתווסף לטבלת הצדדים השלישיים. ייתכן שנדרש DPA מול הספק, וזה **דורש בדיקה משפטית** אצל המפעיל.

## 8. בדיקות

- **שרת OIDC אמיתי בתוך תהליך הבדיקה:** ‏`oidc-provider` (תלות פיתוח בלבד).
- **מקרים:**
  - התחברות מלאה.
  - קישור לפי אימייל מאומת, וסירוב לאימייל שלא אומת.
  - מצב הזמנות.
  - דומיינים מותרים.
  - ‏`state` חד-פעמי ופג תוקף.
  - ‏`returnTo` זדוני.
  - ‏MFA אחרי SSO.
  - ניתוק זהות.
  - ייצוא ומחיקה.
- **מסך הניהול:** כפתור ההתחברות והודעות השגיאה, כולל axe.
- **פתוח:** התנהגות Google ו-Microsoft עצמם **דורשת אימות מול התיעוד הרשמי** ובדיקה ידנית. למשל, האם Microsoft שולח `email_verified`. אם לא, קישור לפי אימייל לא יתבצע, וידרוש הזמנה.

## 9. תוצאות

**שרת:**

- ‏`modules/auth/oidc.ts`, שמבוסס על `openid-client` 6.8.8.
- הגנות: PKCE (S256), ‏`state` חד-פעמי ב-Valkey (GETDEL) שקשור לדפדפן בעוגייה, ו-`nonce`.
- קוד ההרשאה מוסר מהלוגים: כתובת ה-callback נרשמת בלי ה-query.
- מיגרציה `0012`.

**שינויים שעלו בבנייה:**

- **מחיקת חשבון בלי סיסמה:** חשבון SSO בלי סיסמה לא היה יכול למחוק את עצמו (זכות לפי GDPR). עכשיו הוא מאשר את המחיקה בהתחברות ב-15 הדקות האחרונות.
- **ניתוק זהות:** אסור לנתק את דרך ההתחברות היחידה.
- **‏MFA אחרי SSO:** הטוקן עובר ב-fragment של הכתובת, שלא נשלח לשרתים או ב-Referer, ונמחק מהכתובת מיד.
- **סוד הבדיקות:** סוד הלקוח בבדיקות נוצר אקראית, כדי ש-gitleaks לא יתריע.

**בדיקות:**

- 8 בדיקות שרת מול ספק OIDC אמיתי בתוך התהליך (`oidc-provider` 9.12.2), ועוד בדיקות ל-`safeReturnTo`.
- המקרים שנבדקו:
  - קישור לפי אימייל מאומת, ואחר כך זיהוי לפי `sub`.
  - סירוב לאימייל שלא אומת.
  - מצב הזמנות, ‏`hasPassword=false` ומחיקה.
  - דומיינים מותרים.
  - שימוש חוזר ב-callback, דפדפן זר (CSRF) וביטול אצל הספק.
  - ‏MFA.
- 3 בדיקות במסך הניהול: הכפתור, הודעות שגיאה (כולל קוד לא מוכר), ו-MFA מה-fragment.
- כל 280 בדיקות השרת עוברות.

**פתוח:**

- בדיקה ידנית מול Google ו-Microsoft: **דורש אימות מול התיעוד הרשמי**.
- ספק לכל ארגון: נדחה.

## תיקונים אחרי סקירת אבטחה

- **חשבון שלא אומת:** בכניסה דרך הספק הוא מאופס (ראו ב-Threat Model). נבדק בבדיקה ייעודית.
- **‏Cookie המצב:** השם הוא `__Secure-rubinny_oidc`. דפדפנים דוחים `__Host-` בלי `Path=/`, ולכן הכניסה נכשלה בכל שרת https. נבדק בבדיקה ייעודית.
