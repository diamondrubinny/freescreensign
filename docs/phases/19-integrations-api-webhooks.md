# שלב 19: אינטגרציות: מפתחות API ו-Webhooks

**סטטוס:** אושר מראש ("המשך ואישור מראש", 28.10.2026). 19.1–19.3 בוצעו (שרת, Webhooks ולוח הניהול), והתיעוד ב-[docs/INTEGRATIONS.md](../INTEGRATIONS.md).

## 1. מטרה

מערכות אחרות בארגון יכולות לדבר עם Rubinny בלי לוח הניהול:

- **מערכת כיבוי אש או בקרת מבנה** מפעילה התראת חירום על המסכים, ומסיימת אותה.
- **מערכת תורים, מערכת קופה או סקריפט** מעדכנת את הטקסט של Widget ("התור הבא: 42", "המבצע של היום").
- **מערכת ניטור** בודקת אילו מסכים מחוברים.
- **Rubinny מודיע החוצה (Webhooks):** מסך התנתק או חזר, התראת חירום התחילה או הסתיימה, שינוי מחכה לאישור. למשל ל-Slack, ל-Teams או ל-n8n.

זה סעיף 1 ב-Roadmap D5 ‏("Webhooks") שעוד לא בוצע.

## 2. החלטות

| #   | החלטה                                                                                                                                                                                                                                                                             |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| B1  | **מפתח API שייך לארגון, לא לאדם.** רק מנהל יוצר אותו, ובארגון שדורש MFA למנהלים צריך MFA. המפתח מוצג פעם אחת בלבד. בשרת נשמר רק SHA-256 שלו: המפתח אקראי, 32 בתים, ולכן אין צורך ב-Argon2.                                                                                        |
| B2  | **הרשאות מצומצמות (scopes)** לכל מפתח: `screens:read`, ‏`alerts:write`, ‏`widgets:write`. אין מפתח "שעושה הכול": אין גישה למשתמשים, למדיה, להגדרות או למפתחות אחרים.                                                                                                              |
| B3  | **נתיב נפרד:** ‏`/api/integrations/v1/...` עם `Authorization: Bearer rbk_...`. בלי עוגיות, ולכן בלי CSRF. קצב מוגבל לכל מפתח. תוקף לא חובה, וביטול מיידי.                                                                                                                         |
| B4  | **‏`widgets:write` רק ל-Widgets של טקסט וטקסט רץ, ורק לשדות התוכן** (הטקסט והכותרת). בארגון שדורש אישור תוכן, השינוי לא עוקף את האישור: התשובה היא 409, ואפשר לבטל את דרישת האישור או להשתמש בהתראות חירום.                                                                       |
| B5  | **יומן פעולות:** כל פעולה של מפתח נרשמת עם שם המפתח, ובלי ה-token. בכל מפתח נשמרים "שימוש אחרון" ו-IP אחרון (קטוע ל-/24).                                                                                                                                                         |
| B6  | **Webhooks:** כתובת https בלבד. השליחה עוברת דרך `safeFetch`, עם הגנת SSRF ובלי כתובות פנימיות, אלא אם המפעיל התיר. החתימה היא HMAC-SHA256 עם סוד לכל Webhook, שנשמר מוצפן (KeyRing). כותרות: `Rubinny-Signature: t=<unix>,v1=<hex>` ו-`Rubinny-Event`.                           |
| B7  | **מסירה:** טבלת `webhook_deliveries` היא תור עמיד, וטיימר בשרת שולח ממנה. בכשל יש עד 6 ניסיונות עם המתנה הולכת וגדלה (1, 5, 30 דקות, 2, 6 ו-12 שעות). כל משלוח נתפס באופן אטומי, כך שגם כמה שרתים לא שולחים פעמיים. אחרי 20 כשלונות רצופים ה-Webhook מושבת, והמנהלים מקבלים מייל. |
| B8  | **תוכן האירוע מינימלי:** מזהים, שמות מסכים, סוג וזמן. לא נשלחים אימיילים, שמות של אנשים או כותרות של פגישות.                                                                                                                                                                      |
| B9  | **מגבלות:** עד 20 מפתחות ועד 10 Webhooks לארגון. גוף בקשה עד 16KB. נשמרים 7 ימים של משלוחים.                                                                                                                                                                                      |

## 3. User Stories

1. **מנהלת IT:** יוצרת מפתח "מערכת כיבוי" עם `alerts:write` בלבד, מעתיקה אותו פעם אחת, ומגדירה אותו במערכת הכיבוי.
2. **מערכת הכיבוי:** שולחת `POST /api/integrations/v1/alerts` עם סוג "evacuation", וכל המסכים מציגים פינוי תוך שניות.
3. **קופה:** מעדכנת כל דקה את הטקסט של Widget "התור הבא".
4. **צוות IT:** מקבל הודעה ב-Teams כשמסך בלובי מתנתק, דרך Webhook ל-n8n.
5. **מנהל:** רואה מתי כל מפתח היה בשימוש לאחרונה ומבטל מפתח שדלף. מהרגע הזה המפתח לא עובד.
6. **משתמש מקלדת או קורא מסך:** מנהל מפתחות ו-Webhooks בטפסים נגישים. המפתח שנוצר מוכרז, ויש כפתור "העתקה".

## 4. API (ציבורי, לאינטגרציות)

| Method | Path                                  | Scope           | מה                                                       |
| ------ | ------------------------------------- | --------------- | -------------------------------------------------------- |
| GET    | `/api/integrations/v1/screens`        | `screens:read`  | מסכים: מזהה, שם, מחובר, נראה לאחרונה, גרסת נגן, פלטפורמה |
| GET    | `/api/integrations/v1/alerts`         | `alerts:write`  | התראות פעילות                                            |
| POST   | `/api/integrations/v1/alerts`         | `alerts:write`  | הפעלת התראה (אותו גוף ואותה ולידציה כמו בלוח הניהול)     |
| POST   | `/api/integrations/v1/alerts/:id/end` | `alerts:write`  | סיום התראה                                               |
| PATCH  | `/api/integrations/v1/widgets/:id`    | `widgets:write` | עדכון `text` / `title` של Widget טקסט או טקסט רץ         |

**ניהול (בלוח הניהול, מנהל בלבד):**

- `GET|POST /api/v1/orgs/:orgId/api-keys` ו-`DELETE .../:keyId`.
- `GET|POST /api/v1/orgs/:orgId/webhooks`, ‏`PATCH|DELETE .../:id`, ‏`POST .../:id/test` ו-`GET .../:id/deliveries`.

**שגיאות:** אותו פורמט כמו בשאר ה-API (`{ error: { code, message } }`). ‏401 למפתח לא תקף, פג תוקף או מבוטל. ‏403 כשחסר scope. ‏404 למשאב של ארגון אחר: לא מגלים שהוא קיים.

## 5. סכמת מסד נתונים (migration ‏`0022_integrations`)

- **‏`api_keys`:** ‏`id`, ‏`org_id`, ‏`name`, ‏`prefix` (8 התווים הראשונים, להצגה), ‏`token_hash` (unique), ‏`scopes text[]`, ‏`created_by`, ‏`created_at`, ‏`expires_at?`, ‏`last_used_at?`, ‏`last_used_ip?` (קטוע) ו-`revoked_at?`.
- **‏`webhooks`:** ‏`id`, ‏`org_id`, ‏`name`, ‏`url`, ‏`events text[]`, ‏`secret_enc`, ‏`enabled`, ‏`failure_count`, ‏`disabled_reason?`, ‏`created_by` ו-`created_at`.
- **‏`webhook_deliveries`:** ‏`id`, ‏`org_id`, ‏`webhook_id`, ‏`event`, ‏`payload jsonb`, ‏`attempts`, ‏`next_attempt_at`, ‏`claimed_until?`, ‏`status` (pending, delivered, failed), ‏`last_status_code?`, ‏`last_error?` (קצר) ו-`created_at`.
- **‏RLS:** ‏`tenant_isolation` על שלוש הטבלאות, כמו בכל טבלה של ארגון.
- **אימות מפתח:** החיפוש לפי `token_hash` נעשה מחוץ להקשר הארגון, כמו טוקן של מסך. אחר כך הבקשה רצה בטרנזקציה של הארגון של המפתח.

## 6. אבטחה (Threat Model)

| איום                      | הגנה                                                                                                              |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| מפתח דולף                 | Scopes מצומצמים, ביטול מיידי, תוקף לא חובה, "שימוש אחרון", יומן פעולות וקידומת `rbk_` (לסורקי סודות כמו gitleaks) |
| ניחוש מפתח                | 256 ביט אקראיים, קצב מוגבל לפי IP על כשלי אימות, והשוואת hash                                                     |
| SSRF דרך Webhook          | ‏https בלבד, ‏`safeFetch` (חסימת כתובות פנימיות, הפניות וגודל), ובלי לקרוא את גוף התשובה מעבר ל-1KB               |
| זיוף Webhook מול המקבל    | חתימת HMAC עם זמן (חלון 5 דקות להגנה מ-replay), וסוד לכל Webhook                                                  |
| עקיפת אישור תוכן          | ‏`widgets:write` מחזיר 409 בארגון שדורש אישור                                                                     |
| דליפת מידע אישי ב-Webhook | תוכן מינימלי (B8)                                                                                                 |
| הצפת יעד או השרת          | תור עם ניסיונות מוגבלים, השבתה אוטומטית ומגבלת קצב                                                                |
| גישה בין ארגונים (IDOR)   | כל שאילתה מסוננת לפי הארגון של המפתח, ו-RLS כהגנה נוספת                                                           |

## 7. פרטיות

- **מפתח:** נשמר רק ה-hash שלו. ה-IP האחרון נשמר קטוע (‎/24 ב-IPv4, ‏‎/48 ב-IPv6) למשך חיי המפתח.
- **Webhooks:** מעבירים מידע לצד שלישי שהמנהל בוחר. לכן מוצגת בעורך הודעה ש"המידע (שמות מסכים ומצבם) יישלח לכתובת שתגדירו, ובאחריותכם לוודא שמותר". ‏**דורש בדיקה משפטית** כשהיעד מחוץ לארגון, למשל DPA מול ספק Slack.
- **שמירה:** משלוחים נשמרים 7 ימים ונמחקים בתחזוקה היומית.

## 8. לוח הניהול

עמוד חדש "אינטגרציות", שמוצג למנהלים בלבד. יש בו שני חלקים:

- **מפתחות API:**
  - רשימה עם שם, קידומת, הרשאות, תוקף, שימוש אחרון וכפתור "ביטול".
  - "מפתח חדש" נפתח בדיאלוג. המפתח מוצג פעם אחת, עם "העתקה" והודעה מוכרזת.
- **Webhooks:**
  - רשימה עם כתובת, אירועים, מצב (פעיל או מושבת, ולמה) וכפתור "שליחת בדיקה".
  - לכל Webhook יש עשרת המשלוחים האחרונים: סטטוס, קוד וזמן.
  - הסוד מוצג פעם אחת, ואפשר להחליף אותו ("סוד חדש").

עברית ואנגלית, RTL ונגישות כמו בשאר הלוח.
